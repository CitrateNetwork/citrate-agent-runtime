# HUP-S4.4: a review screen is only as honest as what it binds to

S4.1 built a host that treats every MCP server as a stranger. S4.4 lets a member
introduce new strangers: Settings > MCP servers in citrate-core, a stricter
validator and a dry-run probe here.

**The review must show the code that will run.** A review screen that shows
`/opt/notes/bin/notes-mcp --root ~/notes` is misleading if the entry also sets
`DYLD_INSERT_LIBRARIES` or `NODE_OPTIONS=--require ...`. So user entries refuse the
env names that change what a process loads. The same reasoning made `$X`, `${X}` and
`%X%` values an error rather than a literal: nothing is expanded and nothing is
inherited, and a member who types `${HF_TOKEN}` almost certainly expected
inheritance, so the honest response is to say so, not to pass the string through.

**One offer decision, two callers.** The probe answers "which tools would a session
get?" If it computed that separately from the host, the review screen could drift
from reality. The host's offer logic moved into one function both use; the review
is the session's decision, shown early.

**The token binds the review to the entry, not to the name.** Core enables a server
only with a review token derived from the fingerprint of the entry as probed
(command, args, folder, URL, env values, the write switch), salted per app session
so the fingerprint itself, a hash over secrets, never crosses into the webview. An
edit, a rename, or an app restart all mean a fresh check. A check whose report
claims a trusted tool is not recorded at all.

**What we did not build.** The probe needs the sidecar running; core says so
instead of spawning servers itself, so there is one place that starts MCP servers.
Changes still apply at the next Hermes start. Two mutants survive by design (the
probe's outer deadline and a redaction path are both backed by a second guard), and
are written down in the crate README rather than papered over.
