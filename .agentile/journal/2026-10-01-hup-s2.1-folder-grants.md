# HUP-S2.1 (runtime half): folder grants

New crate `agent-grants`: member folder grants, a read-only 24 h full-access
grant, expiry at use time, immediate revocation, a serde document for core to
store, a TLA+ model and a traversal fuzz. Not wired into sessions, file tools
or the core UI; those are later work.

## What was lifted, what was not

`agent-legacy` has two older path checks (`adapters/sandbox.rs`,
`mcp_server.rs`). The new crate keeps their sound parts (component-wise
containment, separate read and write) and takes resolution from agent-guard,
which walks in kernel order and checks every location it visits. Roots are
stored canonical, so swapping a granted folder for a symlink later grants
nothing. The on-disk spelling step (`std::fs::canonicalize` on the existing
part, then the guard again on that spelling) exists for case-insensitive
volumes, where `~/Work` and `~/work` are the same folder.

## The finding

The first `check` handed every live folder grant's root to the guard as a
`.env` project root and then took any grant that covered the path. Unit tests
and the fuzz were green. TLC was not: a shallow folder grant on a high folder
makes that folder a project root without covering a `.env` two levels down,
and full access then covers the file. The model said it in a short trace;
writing it as a Rust test took one fixture and failed on the first run. The
fix is two phases (folder grants with their roots; then full access with no
project roots).

Lesson: the `.env` rule is a property of *which grant allows*, not of the set
of grants. Any time a lower layer takes a set (project roots) and an upper
layer picks one element (the covering grant), the two can disagree. The model
caught it because `DotEnvOnlyViaFolderGrant` was stated about the grant that
allowed, not about the guard's inputs.

## Model hygiene

The first model kept the last decision in a variable and ran past 4 million
distinct states. Making `Decide` a pure function of the state and quantifying
the invariants over every request removed the history and finished in about a
minute and a half. A second lesson came from mutation: three mutants survived
the first run. Two (full access writable, full-access TTL off by one) survived
because the action that issues grants only ever offered valid requests, so the
guard inside it was never exercised; offering invalid requests too (write,
zero and over-limit TTLs for full access) killed them. The third (the
grant-root deny check removed) survived because the check-time deny list
already blocks every access under such a root; no invariant said a grant may
not be rooted there. `NoGrantRootedInDenyList` now does.

## Review addendum (adversarial review, same night)

The model only issues grants at the current clock, so it never sees a stored
grant dated ahead of it. In the Rust code, `is_active` ignored `granted_at`:
a loaded full-access grant with `granted_at` far in the future passed the
24 h load check (it compares `expires_at - granted_at`) yet was live from now
until long after now + 24 h. The window is now `[granted_at, expires_at)`,
with a red test first (`a_stored_grant_is_inert_before_its_granted_at`) and a
`NotYetActive` status for the Grants list. A clock moving backwards now makes
grants briefly inert, which fails closed. The two "second look" checks in
`resolve_checked` (guard re-run on the on-disk spelling, and the equality
test) defend against a path changing mid-check; single-edit mutants of each
survive the suite because no deterministic test can stage that race.
